# CLAUDE.md — Realty Radar

Инструкции для сессий Claude Code (и для разработчиков). Прочитайте целиком перед изменениями.

## Что это

Realty Radar — внутренняя система сбора, хранения, анализа и сравнения данных по рынку
новостроек и конкурентным проектам: лоты и цены, квартирография, планировки, продуктовые
характеристики, локация, проектные декларации (наш.дом.рф).

**Текущее состояние:** реализован **Core MVP** (`src/modules/core`, фактическое состояние —
`docs/architecture/core-mvp.md`). Остальные бизнес-модули — только пакеты-границы
`src/modules/*/doc.go`. Следующий этап — импорт PDF с AI-извлечением (Data Collection); он
начинается **отдельной задачей**. Не начинайте реализацию модулей и этапов по своей инициативе.

## Источник требований — главное правило

- **Исходное ТЗ — источник бизнес-требований:**
  `docs/requirements/source/ТЗ для приложения сбора данных по новостройкам.docx`.
  Читаемая копия — `docs/requirements/source/tz-text.md` (при расхождении верен .docx).
- **Если код, документация и ТЗ расходятся, нельзя считать код правильным.** Расхождение
  нужно найти, зафиксировать (в `docs/requirements/open-questions.md` или в описании задачи)
  и сообщить пользователю. Молча «исправлять» требования под код или код под свою
  трактовку нельзя.
- **Не придумывайте отсутствующие бизнес-требования** (пороги, формулы, классификации,
  словари, методики). Неопределённость → вопрос в `docs/requirements/open-questions.md`
  (формат `Q-<AREA>-NN`). Если без решения не продвинуться → явное временное допущение в
  `docs/requirements/assumptions.md` со ссылкой на вопрос. Допущение реализуется так, чтобы
  его было легко заменить.
- Границы системы и соответствие разделов ТЗ модулям — `docs/requirements/scope.md`.

## Архитектура (кратко)

- **Модульный монолит** (ADR-0001): один Go-бинарник, одна БД PostgreSQL, бизнес-модули с
  явными границами.
- **Core — центр** (ADR-0004): Core не зависит от бизнес-модулей. Остальные модули по
  умолчанию зависят только от публичных контрактов Core. Core хранит только данные своей
  доменной ответственности.
- **Слои внутри модуля:** `internal/domain` ← `internal/app` ← `internal/adapters/*`.
- **Внешние системы и AI/ML — адаптеры за портами** (интерфейсами, объявленными в `app`
  модуля).
- **Связывание — только в `src/app`** (composition root).

## Структура проекта

```
src/
  cmd/realtyradar/     точка входа: serve | migrate up|down|status | demo | version
  app/                 composition root (без бизнес-логики)
  platform/            техническая инфраструктура, ничего не знает о модулях
    config/            загрузка RR_* переменных
    logging/           slog
    database/          пул pgx
    migrate/           goose-провайдер
    httpserver/        сервер, middleware, /healthz, /readyz
  web/                 UI-оболочка: layout, шаблоны, статика
  modules/<module>/    бизнес-модули (core — Core MVP; остальные — только doc.go)
migrations/            SQL-миграции всех модулей (встраиваются в бинарник)
tests/architecture/    тест правил зависимостей
tests/integration/     тесты с реальным PostgreSQL (build tag integration)
scripts/               check.sh, test-integration.sh
docker/, docker-compose.yml, .github/workflows/ci.yml
docs/                  architecture, requirements, decisions
```

Устройство модуля (создавайте каталоги только когда они нужны):

```
src/modules/<module>/
  module.go            публичный API: конструктор, RegisterRoutes, сервисы/DTO для других модулей
  internal/domain/     сущности, value objects, правила — чистый Go
  internal/app/        use cases + порты (интерфейсы репозиториев и внешних сервисов)
  internal/adapters/postgres/   репозитории
  internal/adapters/http/       обработчики и шаблоны страниц модуля
  internal/adapters/<external>/ внешние системы (sources/<site>, nashdomrf, …)
```

## Правила зависимостей (проверяет `tests/architecture`)

1. Модули используются другими модулями **только через корневой пакет**
   `realtyradar/src/modules/<module>`. Пакеты `internal/` закрыты компилятором.
2. `core` не импортирует другие модули. Остальные модули **по умолчанию** импортируют
   только публичный контракт `core` (корневой пакет; для данных — опубликованные Core
   представления).
   Прямая зависимость между некорневыми модулями допускается только при реальной
   бизнес-необходимости: **отдельный ADR** + разрешение в `allowedModuleDeps` с комментарием
   со ссылкой на ADR. Любая новая межмодульная зависимость → ADR + изменение
   архитектурного теста. Не добавляйте зависимость «на будущее».
3. `internal/domain` не импортирует `platform`, `web`, `net/http`, `database/sql`, pgx и
   не-domain пакеты своего модуля. `internal/app` не импортирует адаптеры своего модуля.
4. `platform` не импортирует `modules`, `web`, `app`. `web` не импортирует `modules`, `app`.
   Модули не импортируют `app`.
5. Новый каталог в `src/modules` нужно зарегистрировать в `allowedModuleDeps`.

Не ослабляйте тест ради своего изменения. Если правило мешает, это архитектурный вопрос:
обсудите его или оформите ADR.

**Владение данными (ADR-0004):** не переносите данные в Core только для того, чтобы ими
обменивались другие модули. Базовые характеристики Project/Lot — Core; результаты анализа
планировок — Floor Plans; рассчитанные характеристики локации — Location; оценки продукта —
Benchmark. Не добавляйте в Core поля «на будущее» для результатов других модулей. Если
модулю нужны данные нескольких модулей, не стройте заранее read model или агрегирующий
модуль. Сообщите о сценарии и предложите вариант через ADR: явная зависимость через
контракт, read/reporting model или агрегирующий модуль.

## Коллекторы, парсеры, интеграции

- **Коллекторы и парсеры не смешиваются с Core.** Они живут в
  `src/modules/collection/internal/adapters/sources/<source>/`, не пишут в схему `core` и
  передают нормализованные данные только через публичный ingestion API Core.
- Новая внешняя интеграция:
  1. порт (интерфейс) в `internal/app` модуля, которому она нужна;
  2. адаптер в `internal/adapters/<name>/`; HTTP-клиенты с таймаутами; ключи и URL — через
     `RR_*` конфигурацию (добавить в `config.go` и `.env.example`);
  3. тесты адаптера на сохранённых фикстурах ответов (без реальной сети в unit-тестах);
  4. запись в таблицу внешних систем `docs/architecture/overview.md`;
  5. если это новый класс инфраструктуры (очередь, хранилище, ML-сервис, платный API) → ADR.
- AI/ML/OCR-компоненты — только адаптеры за портами (например, в `floorplans`). Домен не
  знает, какой движок используется.
- **Scope MVP (2026-09-15):** автоматический сбор с сайтов — future scope. Не проектируйте
  парсеры сайтов, browser automation и инфраструктуру ради scraping. Основной канал MVP — импорт
  PDF с AI-извлечением и обязательным подтверждением пользователем (`docs/architecture/pdf-extraction.md`,
  ADR-0008 — Принят). Результат AI не пишется в Core без подтверждения; AI-провайдер не
  выбран и подключается только адаптером за портом после отдельного ADR.
- Юридические рамки сбора (Q-GEN-07) не определены — не добавляйте обход антибот-защиты,
  прокси и т. п. без решения пользователя.

## UI и BI (ADR-0005)

- **SSR + htmx — решение для MVP.** Страницы рендерятся `html/template` в
  `internal/adapters/http` модулей, общий layout — в `src/web`. htmx и библиотека графиков
  (кандидат — ECharts) подключаются с первой страницей, которой они нужны.
- Для отдельного сложного виджета допустим изолированный JS-«остров» без сборки.
- **Контрольная точка — реализация Offer Analytics.** Оцените, укладывается ли интерактивная
  аналитика в SSR + htmx, и запишите результат в `docs/architecture/modules.md` (раздел Offer
  Analytics). Если нужна значительная доля клиентского состояния (признаки — в ADR-0005),
  сообщите об этом и предложите отдельный ADR о React/TypeScript. Сами не переходите.
- **Не добавляйте React/TypeScript, SPA, npm-сборку и отдельный фронтенд-проект без нового
  ADR.**
- **Показатели вычисляются в модулях** (use cases в Go или SQL-представления модуля). Не
  вычисляйте их в шаблонах, JS или вычисляемых полях BI. HTTP-адаптер только рендерит
  данные.
- **DataLens — допустимый внешний BI, решение об использовании не принято.** Если его
  подключат: только к опубликованным представлениям, только ролью PostgreSQL на чтение,
  без зависимости кода приложения от DataLens.

## Работа с БД

- PostgreSQL 17, драйвер pgx v5 (`pgxpool`). ORM не используется. SQL пишется явно
  (в Core MVP — вручную на pgx; sqlc — направление ADR-0002, пока не подключён).
- **Схема на модуль** (`core`, `offeranalytics`, `collection`, …). **Писать в схему может
  только модуль-владелец.** Читать чужие данные — через API модуля или опубликованные
  владельцем views. Внешние ключи — только на `core` (между некорневыми модулями — только если
  их зависимость разрешена ADR).
- SQL-запросы — только в `internal/adapters/postgres` модулей. `platform/database` не
  содержит запросов.
- Соглашения (ADR-0003): `snake_case`, таблицы во множественном числе; PK `uuid` (UUIDv7 из
  приложения); `timestamptz` в UTC; деньги `numeric(15,2)`; площади `numeric(10,2)`;
  перечисления — `text` + `CHECK` или справочник, не PG `enum`; `jsonb` — только для
  действительно переменной структуры.
- История: неизменяемые наблюдения (collection) + версии состояния лота при изменении
  (core, `valid_from`/`valid_to`, `last_observed_at`; ADR-0007). Производные показатели
  должны пересчитываться из исходных данных.
- **Состояние лота меняется только через входной контракт Core `IngestObservationBatch`**:
  ручной ввод, будущий импорт PDF, будущий сбор. Прямые UPDATE версий и отдельные «формы
  редактирования» в обход контракта запрещены: изменение должно оставаться наблюдением с
  источником и моментом. Цена за м² и размер скидки не хранятся (Q-CORE-15).
- Файлы (скриншоты, PDF, сырые ответы) — не в БД. В БД только метаданные.
- Всегда передавайте `context.Context`. Параметризованные запросы, никакой конкатенации SQL.

## Миграции

- goose, `migrations/<UTC YYYYMMDDHHMMSS>_<module>_<описание>.sql`, секции
  `-- +goose Up` и `-- +goose Down` обязательны.
- Миграция модуля меняет только схему модуля (исключения, например `CREATE EXTENSION`, —
  с комментарием).
- **Применённую миграцию не редактируют** — только новая миграция.
- Команды: `go run ./src/cmd/realtyradar migrate up|down|status`.
- После добавления миграции запустите интеграционные тесты (`up → down до 0 → up`).

## Именование

- Go: стандартный стиль (`gofmt`, короткие имена пакетов в нижнем регистре без `_`),
  экспортируемое — с комментарием. Пакеты модулей — одно слово (`offeranalytics`).
- Идентификаторы, схема БД, логи, сообщения об ошибках — на английском. Комментарии в
  коде — на английском. Документация — на русском. Тексты UI — на русском.
- Переменные окружения — `RR_<AREA>_<NAME>`.
- Ошибки оборачиваются с контекстом: `fmt.Errorf("load lot %s: %w", id, err)`.
- Предметные термины: используйте глоссарий из кода Core (появится в Module 1). Не вводите
  синонимы (lot ≠ unit ≠ apartment без необходимости; квартира — тип лота).

## Тесты

- Unit-тесты — рядом с кодом (`*_test.go`), стандартный `testing` и `httptest`, без сети и БД.
- Доменная логика и расчёты показателей покрываются unit-тестами обязательно, с табличными
  тестами и граничными случаями (пустые выборки, медиана при чётном числе значений, нулевая
  площадь).
- Репозитории и миграции — интеграционные тесты в `tests/integration`
  (`//go:build integration`, реальный PostgreSQL из `RR_TEST_DATABASE_URL` — **отдельная
  тестовая БД**).
- Парсеры — тесты на сохранённых фикстурах (HTML/JSON/PDF) рядом с адаптером в `testdata/`.
- Перед завершением задачи:
  - `bash scripts/check.sh` (gofmt, vet, unit и архитектурные тесты);
  - `bash scripts/test-integration.sh`, если менялись БД, миграции или репозитории.
- Не отключайте и не пропускайте падающие тесты, чтобы «зазеленить» сборку. Сообщайте о них.

## Документация и ADR

- **Существенное архитектурное решение → ADR** в `docs/decisions/` (шаблон и реестр —
  `docs/decisions/README.md`): новая технология или инфраструктура, изменение границ или
  зависимостей модулей, подхода к хранению. Принятые ADR не переписываются — их заменяет
  новый ADR.
- **При изменении архитектуры обновите документацию в том же изменении:**
  `docs/architecture/*`, этот файл, `README.md`, `.env.example`.
- Документация описывает то, что есть. Планируемое явно помечается как «планируется».
  Не описывайте несуществующую реализацию как готовую.
- Реализованный модуль получает раздел «Статус / реализовано» в `docs/architecture/modules.md`
  и обновлённый `doc.go`.
- Новые вопросы и допущения — в `open-questions.md` и `assumptions.md` в процессе работы, а
  не в конце.

## Команды

```bash
docker compose up -d postgres                     # БД (или свой PostgreSQL 17)
cp .env.example .env                              # локальная конфигурация
go run ./src/cmd/realtyradar migrate up
go run ./src/cmd/realtyradar demo                 # демонстрационные данные (идемпотентно)
go run ./src/cmd/realtyradar serve                # http://localhost:8080
bash scripts/check.sh                             # быстрые проверки
RR_TEST_DATABASE_URL=... bash scripts/test-integration.sh
```

На Windows скрипты запускаются через Git Bash. `make` не обязателен (Makefile — обёртки над
теми же командами).
