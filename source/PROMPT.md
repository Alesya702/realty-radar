1. СНАЧАЛА ЗАФИКСИРУЙ ПРИНЯТЫЕ РЕШЕНИЯ
==================================================

Обнови документацию и Proposed ADR с учётом следующих решений.

1. PDF Import / AI Extraction остаётся частью Data Collection.

2. Core не читает PDF, не вызывает AI и не знает AI provider.

3. Extraction Result не является каноническими данными Core.

Будущий поток:

PDF
→ AI Extraction
→ standardized JSON
→ validation
→ user review/correction
→ confirmation
→ Core ingestion

4. Автоматический site scraping не входит в MVP и переносится в future scope.

5. Собственные и внешние проекты находятся в единой модели Core.

Не создавать:
- OurProject;
- CompetitorProject;
- competitor boolean.

Конкурентность является контекстным отношением Project → Project.

Принадлежность проекта портфелю компании и конкурентное отношение — разные понятия.

6. Fuzzy matching в MVP не используется.

Если импортируемый объект невозможно однозначно сопоставить, решение принимает пользователь.

7. Цена:

price = актуальная цена предложения Lot на момент наблюдения.

price_before_discount = базовая/предыдущая цена до явно указанной скидки, если источник её показывает.

Если скидка из источника не следует однозначно:
price_before_discount = null.

Размер/процент скидки в Core отдельно не хранить — он вычисляется при необходимости.

Не выводить price_before_discount из предположений.

8. Детализированные sales terms:
- installment;
- mortgage;
- booking conditions;
- promotion details;
- другие финансовые условия

НЕ являются BLOCKING для Core MVP.

Их структурированная модель переносится на следующий этап / Offer Analytics.

Если такие данные позже извлекаются из PDF, они могут временно оставаться в Extraction Result до появления утверждённой модели.

Обнови open-questions.md:
Q-CORE-15 закрыть указанным выше решением.
Q-CORE-10 снять с BLOCKING и перенести в IMPORTANT/LATER в зависимости от существующей классификации.

4. CORE DOMAIN
==================================================

Реализуй минимально необходимые сущности Core:

- Developer;
- Project;
- Building;
- Section;
- Lot;
- ProjectRelation;
- PortfolioMembership;
- DataSource;
- LotListing;
- LotListingVersion / Lot history.

Phase реализуй только если существующая утверждённая модель показывает, что его наличие сейчас не создаёт лишней сложности.

Иерархия не должна требовать искусственного создания отсутствующих уровней.

Например, Lot может существовать в Project/Building без Section, если источник не содержит секцию.

Используй канонические UUID согласно принятым ADR/CLAUDE.md.

==================================================
5. LOT — MVP
==================================================

Для Lot и его состояния реализуй только поля, которые нужны для базового сценария и последующего PDF Import.

Минимально рассмотри:

identity:
- id;
- lot_type;
- number;

placement:
- project;
- building?;
- section?;
- floor?;

state:
- rooms;
- total_area;
- price;
- price_before_discount;
- status;
- finish;
- view/features только если их реализация не требует искусственного справочника без известных значений;
- presence/listed state;

source/history:
- data source;
- source key?;
- source URL?;
- publication date?;
- observed_at;
- first_seen_at;
- last_seen_at.

Не создавай поля только ради полноты будущей модели.

Не хранить вычисляемый price_per_sqm как каноническое поле, если нет технической причины.
Он может вычисляться:

price / total_area.

==================================================
6. ИСТОРИЯ LOT
==================================================

Историю реализуй достаточно для сценария:

Observation 1:
Lot 145
price = 15 900 000

Observation 2:
тот же Lot 145
price = 16 400 000

После этого система должна уметь показать:

- current state;
- previous states;
- state at date/time;
- когда изменилось значение.

Новая версия создаётся только при изменении значимого состояния.

Повторное наблюдение тех же значений не должно создавать новую бизнес-версию, но должно обновлять last observed/seen согласно принятой модели.

Сохраняй temporal модель так, чтобы позже можно было добавить автоматический сбор.

Но НЕ реализуй сейчас сложные сценарии:
- автоматическое delisting по отсутствию в источнике;
- сложное merge history;
- replay всей истории;
- агрегаторы с несколькими listings;
- fuzzy matching;
- автоматическое определение продажи.

7. DATA SOURCE
==================================================

Core должен быть source-agnostic.

Для MVP достаточно поддержать источники, необходимые для:

- manual entry;
- future document import.

Не реализуй site collectors.

DataSource не должен содержать логику конкретного источника.

9. INGESTION CONTRACT
==================================================

Сохрани архитектурную возможность будущего:

Collection
→ IngestObservationBatch
→ Core.

Но НЕ реализуй всю сложность предложенного универсального ObservationBatch, если она не нужна текущему vertical slice.

Нужен минимальный стабильный контракт, через который следующий этап PDF Import сможет:

- указать Project;
- указать/создать Building/Section при подтверждённом решении;
- создать новый Lot или указать существующий Lot;
- передать подтверждённое состояние;
- указать DataSource;
- указать observed_at;
- записать новую версию состояния.

Если полноценный IngestObservationBatch разумно реализовать сейчас без значительного усложнения — реализуй минимальную MVP-версию.

Документируй, что сознательно отложено.

10. DATABASE
==================================================

Создай реальные миграции Core.

Следуй правилам CLAUDE.md и ADR:

- PostgreSQL;
- schema `core`;
- snake_case;
- UUID;
- numeric для денег/площадей;
- timestamptz / UTC;
- FK и CHECK там, где они действительно защищают инварианты;
- без PostgreSQL ENUM;
- без JSONB вместо нормальной стабильной модели.

Не создавай десятки справочников без утверждённых значений.

Если бизнес-справочник пока неизвестен, выбери минимальное обратимое решение и зафиксируй его.

11. UI — МИНИМАЛЬНЫЙ, НО РАБОЧИЙ
==================================================

Создай минимальный интерфейс, позволяющий руками проверить Core.

Это НЕ финальный дизайн Realty Radar.

Нужно иметь возможность:

1. открыть список проектов;
2. создать Developer;
3. создать Project;
4. добавить Building;
5. при необходимости Section;
6. добавить Lot;
7. открыть карточку Lot;
8. изменить состояние Lot через новое наблюдение;
9. увидеть текущую цену/площадь/статус;
10. увидеть историю изменений.

Также должна быть возможность увидеть:
- собственный/портфельный проект;
- отношения проекта с конкурентами/референсами.

Используй существующий SSR-подход проекта.

Не подключай React и не создавай сложный frontend.

UI должен быть функциональным и достаточно аккуратным для проверки, но не трать этот этап на визуальную полировку.
