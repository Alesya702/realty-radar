Мы начинаем с нуля разработку проекта Realty Radar.

Рабочая папка проекта:
realty-radar

Realty Radar — система сбора, хранения, анализа и сравнения данных по рынку новостроек и конкурентным проектам.

В папке проекта находится исходное ТЗ бизнеса:
«ТЗ для приложения сбора данных по новостройкам.docx».

ВАЖНО:
На этом этапе НЕ нужно реализовывать бизнес-функциональность приложения.
Не нужно писать парсеры сайтов, аналитику, дашборды, обработку планировок или интеграции.

Текущая задача — правильно подготовить структуру проекта для дальнейшей поэтапной разработки.

==================================================
1. СНАЧАЛА ИЗУЧИ ИСХОДНОЕ ТЗ
==================================================

Полностью изучи приложенное ТЗ.

Рассматривай его как исходный документ бизнеса, а не как готовую техническую спецификацию.

Не изменяй и не «исправляй» бизнес-требования молча.

Если требования:
- неоднозначны;
- противоречат друг другу;
- требуют уточнения;
- технически сложны;
- относятся скорее к будущим этапам;

зафиксируй это отдельно.

На основании ТЗ определи границы системы и основные функциональные области.

Предварительно система должна быть разделена минимум на следующие модули:

1. Core / Projects & Lots
   Базовые сущности:
   - девелоперы;
   - проекты / ЖК;
   - корпуса;
   - секции;
   - очереди;
   - лоты;
   - конкуренты;
   - источники данных;
   - история состояния лотов.

2. Apartment Mix Analytics
   - квартирография;
   - структура предложения;
   - распределения;
   - агрегированные показатели;
   - фильтрация;
   - сравнение проектов.

3. Data Collection
   - получение данных с внешних источников;
   - collectors/parsers;
   - импорт;
   - обновление данных;
   - фиксация изменений;
   - контроль качества загрузки.

4. Project Declarations
   - проектные декларации;
   - данные наш.дом.рф;
   - исторические срезы;
   - расчёт общего, проданного и остаточного предложения.

5. Floor Plan Analysis
   - PDF;
   - изображения планировок;
   - распознавание помещений;
   - извлечение характеристик;
   - классификация планировок;
   - поиск похожих планировок.

6. Product Benchmark
   - продуктовые характеристики ЖК;
   - архитектура;
   - благоустройство;
   - инженерия;
   - инфраструктура;
   - сервис;
   - паркинг;
   - безопасность;
   - маркетинг;
   - финансовые условия;
   - будущая система scoring.

7. Location Analytics
   - POI;
   - транспорт;
   - социальная инфраструктура;
   - расстояния;
   - время в пути;
   - физические барьеры;
   - сравнение локаций.

Эта декомпозиция предварительная.
Если после анализа ТЗ ты считаешь, что границы модулей стоит изменить, сначала зафиксируй предложение и объясни причину.

==================================================
2. СПРОЕКТИРУЙ СТРУКТУРУ ПРОЕКТА
==================================================

Создай архитектуру, позволяющую реализовывать эти модули последовательно и относительно независимо.

При этом НЕ создавай семь отдельных приложений или микросервисов без необходимости.

На начальном этапе предпочтительна модульная архитектура одного приложения (modular monolith), если нет веских причин выбрать другое решение.

Core должен быть центральным доменным модулем.

Data Collection, Project Declarations, Floor Plan Analysis и Location Analytics в дальнейшем должны иметь возможность подключаться к Core, не заставляя переписывать его бизнес-логику.

Не допускай сильного смешивания:
- UI;
- бизнес-логики;
- работы с БД;
- внешних интеграций;
- парсеров;
- AI/ML-компонентов.

==================================================
3. ПРЕДЛОЖИ ТЕХНОЛОГИЧЕСКИЙ СТЕК
==================================================

До создания структуры проанализируй требования и предложи разумный стек для MVP и последующего развития.

Учитывай:
- приложение должно быть реализовано на Go
- веб-интерфейс;
- аналитические таблицы и графики;
- потенциально большой объём лотов;
- хранение исторических данных;
- фоновые задачи;
- будущий scraping;
- обработку PDF;
- AI/CV-анализ планировок;
- геоданные и внешние API;
- возможность локального запуска;
- удобство дальнейшей разработки через Claude Code;
- возможность последующей передачи проекта классическим разработчикам.

Не выбирай сложную инфраструктуру только «на будущее».

Для каждого ключевого технологического решения кратко объясни:
- что выбрано;
- почему;
- какие альтернативы рассматривались;
- какие ограничения есть у решения.

==================================================
6. ARCHITECTURE DECISION RECORDS
==================================================

Создай каталог:

docs/decisions/

и используй ADR для существенных архитектурных решений.

Как минимум зафиксируй решения по:
- общей архитектуре приложения;
- технологическому стеку;
- подходу к хранению данных;
- разделению модулей.

Не нужно создавать ADR на каждую мелочь.

Каждый ADR должен отвечать на вопросы:
- какой был контекст;
- какое решение принято;
- почему;
- какие альтернативы рассматривались;
- последствия решения.

7. CLAUDE.md
==================================================

CLAUDE.md должен быть действительно полезным для последующих сессий Claude Code.

Зафиксируй в нём:

- назначение Realty Radar;
- архитектурные принципы;
- структуру проекта;
- основные модули;
- правила зависимостей между слоями/модулями;
- правила работы с БД;
- правила именования;
- требования к тестам;
- требования к документации;
- правила работы с миграциями;
- правила добавления новых интеграций;
- правило не смешивать collectors/parsers с Core;
- правило фиксировать существенные архитектурные решения через ADR;
- правило не придумывать отсутствующие бизнес-требования;
- правило добавлять неопределённые требования в open-questions.md;
- правило обновлять документацию при изменении архитектуры.

Также явно укажи:

Исходное ТЗ является источником бизнес-требований.
Если код, документация и исходное ТЗ расходятся, нельзя самостоятельно считать код правильным — расхождение необходимо выявить и зафиксировать.
