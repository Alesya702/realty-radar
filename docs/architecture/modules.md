# Модули

> Статус (2026-09-15): **реализован Core MVP** (раздел 3.1, [core-mvp.md](core-mvp.md)).
> Остальные бизнес-модули не реализованы: в коде есть только пакеты-границы
> `src/modules/<module>/doc.go` и правила зависимостей в `tests/architecture`. Состав сущностей
> нереализованных модулей — ориентир по ТЗ, а не утверждённая модель данных. Детальная модель
> каждого модуля проектируется в его этапе.

## 1. Перечень

| # | Модуль | Пакет | Разделы ТЗ | Зависит от |
|---|---|---|---|---|
| 1 | Core / Projects & Lots | `src/modules/core` | п. 1 (конкуренты), п. 3 (атрибуты лота) | — |
| 2 | Offer Analytics (Apartment Mix & Prices) | `src/modules/offeranalytics` | п. 1 (обязательные показатели), п. 2, п. 3 (ценовые показатели) | Core |
| 3 | Data Collection | `src/modules/collection` | п. 3 (сбор), п. 4 (документы-источники) | Core |
| 4 | Project Declarations | `src/modules/declarations` | п. 6 | Core |
| 5 | Floor Plan Analysis | `src/modules/floorplans` | п. 1 (планировки, формулы) | Core |
| 6 | Product Benchmark | `src/modules/benchmark` | п. 4 | Core |
| 7 | Location Analytics | `src/modules/location` | п. 5 | Core |

«Зависит от: Core» означает зависимость от **публичных контрактов** Core: корневого пакета
`src/modules/core` и опубликованных им представлений для чтения. Внутренние пакеты и
таблицы Core контрактом не являются.

Политика зависимостей ([ADR-0004](../decisions/0004-module-boundaries.md)):

1. Core не зависит от остальных бизнес-модулей.
2. Некорневые модули по умолчанию зависят только от публичных контрактов Core.
3. Прямая зависимость между некорневыми модулями допускается только при реальной
   бизнес-необходимости: по отдельному ADR, через публичный контракт модуля-поставщика и с
   разрешением в `allowedModuleDeps` (`tests/architecture/dependencies_test.go`). Сейчас
   таких зависимостей нет.
4. Данные не переносятся в Core исключительно для обмена между модулями. Каждый модуль
   хранит результаты своей работы у себя (см. «Владение данными» в описании модулей).
5. Любая новая межмодульная зависимость требует ADR и изменения архитектурного теста.

Если модулю понадобятся данные нескольких модулей, вариант (явная зависимость через
контракт, read/reporting model или агрегирующий модуль) выбирается при появлении
конкретного сценария. Заранее не проектируется.

## 2. Устройство модуля (соглашение)

Каталоги создаются по мере необходимости. Пустые каталоги «на будущее» не создаются.

```
src/modules/<module>/
  doc.go / module.go      публичный API модуля: конструктор, регистрация маршрутов,
                          сервисы и DTO, доступные другим модулям
  internal/               недоступно другим модулям (гарантия компилятора Go)
    domain/               сущности, value objects, доменные правила; только стандартная
                          библиотека и domain-пакеты своего модуля
    app/                  сценарии использования (use cases) и порты (интерфейсы
                          репозиториев и внешних сервисов)
    adapters/
      postgres/           репозитории, SQL
      http/               HTTP-обработчики и шаблоны страниц модуля
      <external>/         адаптеры внешних систем (например, sources/<site>, nashdomrf)
```

Правила (проверяются тестом):

- другие модули импортируют только корневой пакет модуля;
- `internal/domain` не импортирует `platform`, `web`, `net/http`, `database/sql`, pgx и
  не-domain пакеты своего модуля;
- `platform` не импортирует модули, `web` и `app`; `web` не импортирует модули и `app`;
- `internal/app` не импортирует адаптеры своего модуля;
- модули не импортируют `app`.

## 3. Модули

### 3.1. Core / Projects & Lots

**Ответственность.** Центральная доменная модель рынка и её история. Единственный владелец
канонических данных о проектах и лотах.

**Статус / реализовано (Core MVP, 2026-09-15)** — подробно в [core-mvp.md](core-mvp.md):
- сущности и таблицы: девелоперы, проекты (собственные и внешние в одной модели), корпуса,
  секции, лоты (корпус и секция необязательны), источники данных, размещения лота в источниках,
  пакеты приёма, версии состояния размещения, портфель компании, отношения проектов;
- use cases в `core.Module` и входной контракт `IngestObservationBatch` (MVP-версия): решение о
  сопоставлении передаёт отправитель, fuzzy matching нет, пакет атомарен, поля
  `Value` / `Unknown` / `Absent`;
- история: версия только при изменении, `last_observed_at`, текущее состояние и состояние на момент;
- страницы: проекты, карточка проекта, карточка лота с историей и формой наблюдения, портфель,
  девелоперы, источники;
- демо-данные: `realtyradar demo`.

**Не реализовано (целевая модель):** очереди, поиск кандидатов сопоставления, область и полнота
пакета и автоматическое снятие с публикации, вставка более ранних наблюдений, исправление и
отзыв пакета, слияния, внешние ключи структуры, класс проекта, район, срок сдачи, справочники
видов и особенностей, условия продаж, опубликованные представления.

**Проектирование:** целевая модель — [core-domain-model.md](core-domain-model.md), принятые ADR —
[ADR-0006](../decisions/0006-core-identity-and-source-references.md) (идентичность и
сопоставление) и [ADR-0007](../decisions/0007-lot-history-model.md) (история лота). Уточнения к
списку ниже:
- собственные проекты и портфель компании — в Core;
- реестр источников в Core — только идентичность источника, а «что и откуда получать» — Data
  Collection;
- Core принимает только подтверждённые нормализованные данные (`IngestObservationBatch`); PDF,
  AI и Extraction Result Core не видит;
- сроки сдачи и условия продаж — после ответов Q-CORE-12 и Q-CORE-10.

Расхождения — раздел 17 модели.

**Относится:**
- девелоперы и группы компаний;
- проекты (ЖК), класс проекта, очереди, корпуса, секции, сроки сдачи;
- лоты всех типов (квартиры, коммерция, кладовые, машино-места — см. Q-CORE-02) и их
  атрибуты из ТЗ п. 3 (этаж, номер, комнатность, площадь, цены, скидка, отделка, вид,
  особенности, статус, условия, акции);
- история состояния лотов (версии при изменении), даты первого обнаружения и последнего
  обновления;
- источники данных (реестр: какой сайт или документ, к какому проекту относится);
- конкурентные связи между проектами (прямые / косвенные / референсные) и классы;
- справочники, общие для модулей (типы лотов, отделка, виды, статусы);
- API приёма нормализованных данных (ingestion) для Data Collection;
- API чтения (запросы, опубликованные представления) для аналитических модулей.

**Не относится:**
- HTTP-запросы к сайтам, парсинг HTML/JSON, скриншоты, расписания сбора → Data Collection;
- агрегаты, распределения, премии, динамика цен → Offer Analytics;
- распознавание планировок → Floor Plans;
- продуктовые оценки, POI, декларации → соответствующие модули;
- автоматическое вычисление типа конкурента по критериям — пока не определены правила
  (Q-CORE-06);
- хранение результатов других модулей ради обмена между ними: результаты анализа
  планировок, рассчитанные характеристики локации, оценки продукта, расчёты деклараций.
  В модель Core не добавляются поля «на будущее» для таких данных.

**Зависимости:** нет.

### 3.2. Offer Analytics (квартирография и цены)

**Ответственность.** Аналитика структуры предложения и цен по данным Core. Модуль только
читает данные Core и не меняет их.

**Относится:**
- обязательные показатели (ТЗ п. 1): количество лотов, доступные и проданные, доли типов,
  площади (средняя, медиана, min/max), диапазон цен, цена за м², доля евроформатов и
  уникальных форматов, распределения по корпусам и этажам, стадия предложения;
- квартирография (ТЗ п. 2): срезы по классу, девелоперу, району, корпусу, очереди, типу,
  площади, цене, этажу, отделке, виду, сроку сдачи;
- ценовые показатели (ТЗ п. 3): min/avg/median, по разрезам, премии, изменение за
  день/неделю/месяц/квартал, эффект акций, стоимость с учётом рассрочки, сравнение с
  конкурентами;
- сравнение проектов;
- производные витрины и материализованные агрегаты (пересчитываемые);
- страницы BI-интерфейса этих срезов.

**Не относится:** получение данных, изменение лотов, определение евроформата по геометрии
планировки (это Floor Plans), показатели деклараций. Если срезам понадобятся результаты
Floor Plans, способ получения выбирается по политике зависимостей (п. 1 этого документа).
Результаты при этом не копируются в Core.

**Зависимости:** Core (публичные контракты).

**UI и BI** ([ADR-0005](../decisions/0005-ui-approach-and-bi.md)):
- страницы модуля — SSR + htmx (решение для MVP);
- **контрольная точка:** при реализации модуля оценивается, укладывается ли интерактивная
  аналитика в SSR + htmx. Результат записывается здесь. Если нужна значительная доля
  клиентского состояния (перекрёстная фильтрация виджетов, pivot на клиенте, конструктор
  отчётов и т. п.), вариант React/TypeScript пересматривается отдельным ADR;
- модуль публикует представления для чтения, пригодные и для страниц, и для возможного
  подключения DataLens. Формулы показателей живут в модуле, а не в BI.

**Отличие от предварительной декомпозиции:** в предварительном плане модуль назывался
Apartment Mix Analytics. Ценовые показатели п. 3 добавлены в него — см.
[ADR-0004](../decisions/0004-module-boundaries.md).

### 3.3. Data Collection

**Ответственность.** Получение данных из внешних источников и доставка нормализованных
данных в Core.

**MVP (решение по scope 2026-09-15; архитектура — принятый
[ADR-0008](../decisions/0008-mvp-document-import-ai-extraction.md); не реализовано — следующий
этап после Core MVP):** основной канал MVP — **импорт PDF с AI-извлечением** и ручной ввод. Компонент
импорта документов модуля:
- хранение PDF (порт файлового хранилища `platform`) и метаданных;
- порт AI-провайдера `DocumentExtractor` и адаптеры `internal/adapters/extraction/<provider>`;
  провайдер не выбран;
- Extraction Result (стандартный JSON с версией схемы), валидация, логические проверки;
- черновик импорта: проверка, исправление и подтверждение пользователем, сопоставление с Core
  через запросы Core;
- неизменяемый подтверждённый импорт и отправка пакета в Core (`IngestObservationBatch`);
- факты о планировках и помещениях из PDF хранятся здесь до реализации Floor Plans; передача в
  Floor Plans — отдельный ADR.

Подробно — [pdf-extraction.md](pdf-extraction.md). **Автоматический сбор с сайтов (коллекторы,
парсеры, запуски, скриншоты) — future scope:** пункты списка ниже, относящиеся к нему, не входят
в MVP.

**Относится:**
- коллекторы и парсеры конкретных источников (`internal/adapters/sources/<source>`);
- импорт файлов и ручные загрузки;
- запуски сбора: расписание, статус, ошибки, повторы;
- сырые наблюдения (что показал источник в момент сбора), файлы-доказательства (URL,
  скриншот, исходный ответ);
- нормализация в формат ingestion API Core;
- контроль качества загрузки: полнота, аномалии (например, резкое изменение цены или
  исчезновение всех лотов), отчёт о запуске;
- получение документов проекта (декларация, ДДУ, презентации) как файлов. Способ передачи
  файлов другим модулям выбирается по политике зависимостей при появлении конкретного
  сценария, без переноса ссылок в Core ради обмена.

**Не относится:** бизнес-правила лотов и истории (Core), аналитика, распознавание
содержимого планировок (Floor Plans), данные наш.дом.рф (Declarations — у источника своя
модель данных и ежемесячный цикл).

**Зависимости:** Core (публичные контракты).

### 3.4. Project Declarations

**Ответственность.** Данные проектных деклараций и наш.дом.рф и расчёты по ним (ТЗ п. 6).

**Относится:**
- получение данных наш.дом.рф (адаптер) и ежемесячные исторические срезы;
- привязка объектов декларации к проектам и корпусам Core (Q-DECL-02);
- общий объём: площадь, количество, средняя площадь, квартирография — по типам (квартиры,
  коммерция, кладовые, м/м);
- проданный объём: м², шт., деньги, доли, квартирография; средняя площадь и цена за м²
  проданного;
- остатки: количество, доля, средняя площадь; сравнение «всего / продано / остатки»;
- страницы с таблицами и графиками по декларациям.

**Не относится:** лоты с сайтов (Core и Collection), продуктовые характеристики из
текста деклараций (Benchmark использует декларацию как документ-источник).

**Зависимости:** Core (публичные контракты).

**Почему не часть Data Collection:** у деклараций своя предметная модель (объект
декларации, отчётный срез), свои расчёты и свой ежемесячный цикл. Смешение с поточным
сбором лотов связало бы две разные модели.

### 3.5. Floor Plan Analysis

**Ответственность.** Извлечение и анализ характеристик планировок (ТЗ п. 1).

**Уточнение границы ([ADR-0008](../decisions/0008-mvp-document-import-ai-extraction.md),
принят):** извлечение явно указанных в PDF фактов (подписи и площади помещений,
напечатанные на плане, указанная комнатность) выполняет компонент импорта Data Collection. Floor
Plans отвечает за анализ: типизацию помещений, расчётные показатели, мастер-спальни, проходные
помещения, мокрые зоны, классификацию, похожие планировки. Пограничные случаи —
[pdf-extraction.md](pdf-extraction.md) п. 12. Пункты «приём изображений и PDF» и «помещения и их
площади и подписи» ниже следует читать с этим уточнением: сюда относятся анализ и помещения как
результат анализа, а не извлечение фактов из документов.

**Относится:**
- приём изображений и PDF планировок (файлы от Collection или загрузка вручную);
- порт движка распознавания и его адаптеры (OCR/CV/ML, внешний API — Q-PLAN-09);
- помещения и их площади и подписи, количество комнат и окон;
- расчётные показатели: доля кухни-гостиной, коэффициент полезности / доля жилой площади,
  плотность помещений, мастер-спальни, проходные помещения, окна в санузлах и гардеробных,
  мокрые зоны;
- классификация по шаблонам, поиск похожих планировок;
- проверка и исправление результатов распознавания (если потребуется, Q-PLAN-02).

**Не относится:** цены и статусы лотов, сбор файлов с сайтов, агрегаты квартирографии.

**Владение данными:** результаты анализа планировок хранятся в схеме `floorplans`. На лоты и
проекты модуль ссылается по идентификаторам Core и не записывает результаты в Core.

**Зависимости:** Core (публичные контракты; связь планировки с лотом или проектом).

### 3.6. Product Benchmark

**Ответственность.** Продуктовые характеристики ЖК и их оценка (ТЗ п. 4).

**Относится:**
- каталог групп и параметров (17 групп ТЗ) и значения по проектам;
- различение вариантов характеристики (полноценный клуб / фитнес-зал / студия / партнёрский
  клуб / заявлено, но не подтверждено);
- многомерная оценка: наличие, качество, редкость, значимость для ЦА, подтверждённость;
- источники и доказательства значения (декларация, ДДУ, документация, экспертиза,
  презентация, сайт);
- будущая система scoring (после получения правил от бизнеса).

**Не относится:** получение документов (Collection), локационное окружение (Location),
цены и финансовые условия лотов (Core / Offer Analytics). Группа «Финансовые условия»
описывает продукт на уровне проекта; связь с условиями по лотам — вопрос проектирования
модуля.

**Владение данными:** значения характеристик, их источники и оценки продукта хранятся в
схеме `benchmark`, а не в Core.

**Зависимости:** Core (публичные контракты).

### 3.7. Location Analytics

**Ответственность.** Окружение и доступность проектов (ТЗ п. 5).

**Относится:**
- POI по категориям (транспорт, образование, медицина, спорт, торговля, питание, парки,
  досуг, услуги, религиозные и социальные объекты);
- расстояния (по прямой, пешеходный маршрут) и время в пути (пешком, авто, ОТ, велосипед);
- физические барьеры;
- адаптеры картографических и маршрутных API за портами модуля;
- сравнение локаций проектов;
- геоданные (PostGIS включается миграцией этого модуля при его реализации).

**Не относится:** координаты и адрес проекта как атрибут (хранятся в Core), оценка
продукта, POI как продуктовая инфраструктура внутри ЖК (Benchmark).

**Владение данными:** POI, расстояния, время в пути, барьеры и другие рассчитанные
характеристики локации хранятся в схеме `location`. Базовые координаты и адрес проекта —
данные Core, которые Location читает через публичный контракт.

**Зависимости:** Core (публичные контракты).

## 4. Технические (не бизнес) компоненты

| Компонент | Путь | Может зависеть от |
|---|---|---|
