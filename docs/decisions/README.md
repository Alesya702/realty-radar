# Architecture Decision Records

Существенные архитектурные решения фиксируются здесь, по одному файлу на решение.

## Когда нужен ADR

- выбор или замена технологии, библиотеки, инфраструктурного компонента (очередь,
  хранилище, отдельный сервис);
- изменение границ модулей или разрешённых зависимостей (`allowedModuleDeps`);
- изменение подхода к хранению данных, истории, миграциям;
- решение, которое дорого отменить или которое будет неочевидно следующему разработчику.

Мелочи (имя функции, выбор между двумя эквивалентными способами записи) ADR не требуют.

## Правила

- Имя файла: `NNNN-kebab-case-title.md`, номера по порядку.
- Принятый ADR не переписывается по существу. Если решение меняется, создаётся новый ADR,
  а у старого статус меняется на `Заменён ADR-NNNN`.
- Уточнение формулировок и правил, которое не отменяет решение, вносится в сам ADR с
  отметкой «Уточнён: дата» в шапке и записью в разделе «История изменений».
- После принятия ADR обновите затронутые документы (`docs/architecture`, `CLAUDE.md`,
  `README.md`).

Статусы: `Предложен` · `Принят` · `Отклонён` · `Заменён ADR-NNNN`.
