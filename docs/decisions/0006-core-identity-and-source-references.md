# ADR-0006: Идентичность объектов Core, внешние идентификаторы и сопоставление

- Статус: Принят
- Дата: 2026-09-15 (редакция 2, принята 2026-09-15; см. «История изменений»)
- Связан: [ADR-0003](0003-data-storage.md), [ADR-0004](0004-module-boundaries.md),
  [ADR-0008](0008-mvp-document-import-ai-extraction.md),
  [core-domain-model.md](../architecture/core-domain-model.md) (п. 7, 9)

## Контекст

- ТЗ п. 3 требует «ID лота», «дату первого обнаружения», «дату последнего обновления» и
  отслеживания изменений. Система должна узнавать, что объект, полученный сейчас, — тот же,
  что был получен раньше.
- [уточнение 2026-09-15] Основной источник в MVP — PDF с AI-извлечением и проверкой
  пользователем. В PDF обычно нет внешнего ID, иногда нет номера квартиры, часто есть только
  часть идентифицирующих сведений. В будущем добавится автоматический сбор с сайтов, где проверки
  пользователем нет.
- Внешние ID меняются или отсутствуют, номера бывают условными, один лот может быть в
  нескольких источниках, источники противоречат друг другу.
- Правила дедупликации (Q-CORE-03) бизнесом не заданы; fuzzy matching без подтверждения вводить
  нельзя.
- Другие модули ссылаются на объекты Core по ID (FK, ADR-0003); ссылки не должны ломаться.

## Решение

1. **Канонический ID отделён от внешней идентичности.** UUIDv7 создаёт Core; он не выводится из
   внешних данных, не меняется, не переиспользуется. Другие модули используют только его.
2. **Внешняя идентичность хранится отдельно:** размещение лота `LotListing` (лот × источник, не
   более одного на источник) с необязательными внешними ключами `LotListingKey`; ссылки
   структурных объектов по видам (`ProjectSourceRef`, `BuildingSourceRef`) с FK. Одна полиморфная
   таблица без FK не используется.
3. **`DataSource` — идентичность происхождения** (сайт, канал документов, ручной ввод), а не
   способ получения. Для документов источник — канал, а не отдельный файл.
4. **Ключи сопоставления:** K1 — ключ источника (`native` ID или `derived`-ключ адаптера
   Collection); K2 — ключ размещения (проект, корпус, тип лота, номер). Описательные атрибуты
   (площадь, этаж, цена) — не ключ, только подсказка расхождений.
5. **Минимальная идентичность нового лота:** проект, тип и K1 или K2 (состав подтверждает
   бизнес, Q-PDF-13). Без неё лот не создаётся.
6. **Core выполняет детерминированный поиск кандидатов** (`FindMatchCandidates`) и возвращает
   состояние `matched` / `possible_match` / `new` / `insufficient_identity` с сработавшим правилом.
7. **Кто решает.** Для подтверждаемых пользователем импортов (PDF, ручной ввод) решение принимает
   пользователь и передаёт в пакете явную цель (`existing(lot_id)` / `create_new`). Core повторно
   проверяет решение при приёме (`match_conflict`). Для автоматического сбора Core сопоставляет
   только по K1, создаёт новый лот при минимальной идентичности, остальное отклоняет с причиной.
8. **Fuzzy matching не устанавливает идентичность.**
9. **Дубликаты исправляются явными операциями:** слияние (`merged_into_lot_id`, дубликат не
   удаляется), перенос размещения, слияние корпусов и секций. Core публикует слияния.
10. **Противоречия источников не разрешаются при записи:** у каждого размещения своя история,
    каноническое состояние — из основного размещения (ADR-0007; правило выбора — Q-CORE-18).

## Обоснование

- Стабильный внутренний ID защищает ссылки всех модулей.
- Состояния сопоставления и явная цель в пакете дают один механизм для импорта с проверкой
  (MVP) и для будущего автоматического сбора: различается только то, кто принимает решение.
- Точные ключи предсказуемы и объяснимы пользователю. Ошибка «лишний дубликат» исправляется
  слиянием. «Ложное слияние» разрушительнее, поэтому эвристики требуют решения бизнеса.
- Повторная проверка при приёме защищает от гонок: пока пользователь проверял документ, другой
  импорт мог создать тот же лот.
- Построение `derived`-ключей в Collection удерживает знание об источниках вне Core.

## Рассмотренные альтернативы

| Вариант | Почему отказались |
|---|---|
| Внешний ID как PK или `lots.external_id` | Смена ID ломает ссылки; в PDF ID обычно нет; нет места для нескольких источников |
| Полиморфная таблица ссылок | Нет FK; разные виды объектов требуют разных полей |
| Fuzzy matching (похожие площадь, этаж, цена, название) | Не подтверждён бизнесом; ложные слияния разрушают историю |
| Автоматическое сопоставление по K2 без пользователя | Номера условные, нумерация по секциям, корпус часто неизвестен |
| Сопоставление в Collection (Collection читает таблицы Core) | Нарушает владение данными (ADR-0003); правила идентичности дублировались бы в каждом канале |
| AI сам указывает ID объекта Core | Результат извлечения не должен знать Core; решение о тождестве — не факт документа |
| Каждый PDF — отдельный DataSource | Каждый импорт создавал бы новое размещение; история лота не складывалась бы |

## Последствия

- Проверка импорта в Collection зависит от запросов Core (`FindMatchCandidates`, `GetLotState`) —
  это зависимость от публичного контракта Core, разрешённая по умолчанию.
- Лоты без номера и ключа (например, типовые планировки) не становятся лотами Core.
- Для автоматического сбора без подтверждённого правила K2 смена внешнего ID даёт дубликат,
  который исправляется слиянием.
- Модель «одно размещение на источник» не подходит для агрегаторов с несколькими объявлениями на
  лот (Q-CORE-14, LATER — вместе с автоматическим сбором).
- Модули со ссылками на лоты учитывают слияния.
