# ADR-0005: Подход к UI (SSR + htmx) и возможность использования DataLens

- Статус: Принят
  - SSR + htmx — **решение для MVP** с контрольной точкой при реализации Offer Analytics;
  - React/TypeScript — пересматривается отдельным ADR, только если на контрольной точке
    выявлена потребность в значительном клиентском состоянии (раздел «Решение», п. 2);
  - DataLens — **зафиксирован как допустимый вариант**; решение об использовании не принято.
- Дата: 2026-09-15
- Уточнён: 2026-09-15 — формулировка SSR + htmx (см. «История изменений»)
- Уточняет: [ADR-0002](0002-tech-stack.md) (строки «UI» и «Интерактивность UI»)

## Контекст

- ТЗ описывает результат аналитики как «некий BI-инструмент, который при нажатии кнопок,
  которые являются фильтрами по определенному показателю, выдаёт срез» (п. 2). Кроме того,
  нужны таблицы и графики: «таблица и график из трёх линий» (п. 6).
- ADR-0002 выбрал серверный рендеринг (`html/template`) и назвал htmx направлением, но не
  определил, когда пересматривать подход к UI и как относиться к внешнему BI.
- Самые сложные требования к интерфейсу у модуля Offer Analytics: срезы по 12 измерениям
  квартирографии, ценовые показатели, динамика, сравнение проектов. Именно там может
  возникнуть потребность в сложном клиентском состоянии.
- Бизнес не ответил, нужен ли собственный BI-интерфейс или допустим внешний BI
  ([Q-GEN-10](../requirements/open-questions.md)).
- Команда и стек — Go ([ADR-0002](0002-tech-stack.md)). Отдельный фронтенд-проект означает
  второй язык, сборку и деплой.

## Решение

### 1. Решение для MVP: SSR + htmx

- Страницы рендерятся на сервере (`html/template`). Интерактивность — через **htmx**:
  фильтры, частичное обновление таблиц и блоков, пагинация и сортировка запросами к серверу.
- Графики — JS-библиотека (кандидат — Apache ECharts), которая получает с сервера готовые
  данные. Графики не вычисляют показатели.
- Допускаются **изолированные JS-«острова»** на отдельных страницах, например библиотека
  интерактивной таблицы, без SPA и без сборки фронтенда. Это промежуточный шаг перед
  пересмотром подхода, а не обход этого ADR.
- htmx и библиотеки графиков подключаются, когда появляется первая страница, которой они
  нужны. Сейчас в коде их нет.

### 2. Контрольная точка при реализации Offer Analytics

При проектировании и реализации интерактивной аналитики Offer Analytics выполняется
**обязательная контрольная точка**: оценивается, укладывается ли её сложность в SSR + htmx.
Результат фиксируется:

- **SSR + htmx достаточно** — короткая запись в документации модуля
  (`docs/architecture/modules.md`, раздел Offer Analytics) с датой и обоснованием; решение
  этого ADR остаётся в силе;
- **нужно значительное клиентское состояние** — вариант React/TypeScript пересматривается
  **отдельным ADR**. До его принятия React/TypeScript в проект не добавляется.

Признаки значительного клиентского состояния. Каждый должен подтверждаться прототипом или
реальным сценарием пользователя, а не предположением. Те же признаки применяются, если
они проявятся в другом модуле:

| Признак сложного клиентского состояния | Пример |
|---|---|
| Много взаимозависимых фильтров и виджетов с перекрёстной фильтрацией (клик по графику фильтрует остальные) | Дашборд квартирографии с 10+ связанными срезами |
| Работа с данными на клиенте без round-trip: pivot, перегруппировка, пересчёт на лету | Сводная таблица, где пользователь сам выбирает строки, столбцы и агрегаты |
| Конструктор отчётов, сохраняемые пользовательские представления со сложной конфигурацией | Сохранённый набор срезов и сравнений проектов |
| Задержка серверных round-trip неприемлема для сценария даже после оптимизации запросов | Интерактивное сравнение цен по сотням лотов |
| Число JS-«островов» и объём состояния в них становятся трудно поддерживаемыми | Логика состояния дублируется между сервером и несколькими скриптами |

**Не является** основанием для пересмотра: одна сложная таблица или один сложный график
(решается «островом»), визуальные предпочтения, «на будущее».

Пересмотр оформляется **отдельным ADR**. Он сравнивает React/TypeScript, расширение
SSR + htmx + «острова» и внешний BI (п. 3) и учитывает затраты на второй стек.

### 3. Возможность использования DataLens

Зафиксировано: **Yandex DataLens — допустимый вариант визуализации аналитики** вместо или
вместе с собственными BI-страницами, прежде всего для срезов Offer Analytics и Project
Declarations. Использовать его или нет, в каком объёме и варианте развёртывания (облачный
сервис или self-hosted open-source версия), решается после ответа бизнеса на
[Q-GEN-10](../requirements/open-questions.md) и [Q-GEN-12](../requirements/open-questions.md).

Условия, при которых DataLens не нарушает архитектуру:

- **Показатели определяются в Realty Radar, а не в DataLens.** Формулы (медианы, премии,
  доли, остатки) реализуются в модулях — в Go или в SQL-представлениях модуля. DataLens
  только визуализирует и фильтрует готовые данные. Вычисляемые поля DataLens не должны
  дублировать бизнес-логику: иначе один показатель получит два определения.
- **Подключение — только к опубликованному контракту чтения**
  ([ADR-0003](0003-data-storage.md)): отдельные представления для BI и отдельная роль
  PostgreSQL только на чтение, без доступа к таблицам модулей и сырым данным.
- **DataLens — внешний потребитель, а не модуль.** Код приложения не зависит от DataLens.
  Изменение опубликованных представлений считается изменением контракта.
- Вопросы доступа пользователей, передачи данных во внешний облачный сервис и сетевого
  доступа к БД решаются до подключения (Q-GEN-01, Q-GEN-09, Q-GEN-12).

## Обоснование

- SSR + htmx покрывает основной сценарий ТЗ (фильтры → срез → таблица или график) одним
  языком и одним деплоем. Это соответствует принципу простой инфраструктуры (ADR-0002).
- Контрольная точка и признаки для неё заданы заранее и проверяемо. Решение о React
  принимается по реальной потребности Offer Analytics, а не заранее и не «по привычке».
- Показатели вычисляются на сервере, а данные для UI и BI отдаются через явные контракты.
  Поэтому переход на React (JSON поверх тех же use cases) и подключение DataLens (SQL-представления)
  не требуют переписывать бизнес-логику.
- DataLens может закрыть BI-часть п. 2 ТЗ быстрее собственной разработки. Фиксация условий
  не даёт внешнему инструменту стать вторым местом определения показателей.

## Рассмотренные альтернативы

| Вариант | Почему не выбран сейчас |
|---|---|
| React/TypeScript SPA с самого начала | Второй стек, сборка, деплой и дублирование валидации без подтверждённой потребности; пересматривается на контрольной точке п. 2 |
| Только внешний BI (DataLens или другой) без собственного UI | Бизнес не принял решение (Q-GEN-10); вне BI остаются ввод данных, управление источниками, проверка распознавания и прочие не-BI сценарии |
| Другие BI (Metabase, Superset, Power BI) | Не исключены, но предметно зафиксирована возможность DataLens. Выбор другого BI — отдельное решение |
| Go-генерация графиков на сервере (go-echarts и т. п.) | Ограниченная интерактивность; JS-библиотека графиков с серверными данными гибче при той же архитектуре |

## Последствия

- HTTP-адаптеры модулей не содержат вычислений показателей. Use cases (`internal/app`)
  возвращают данные, адаптер только рендерит HTML (сейчас) или JSON (при необходимости).
- Отдельный фронтенд-проект, npm-сборка и SPA-фреймворки не добавляются без нового ADR.
- При проектировании Offer Analytics выделяются представления, пригодные как контракт чтения
  и для страниц, и для возможного DataLens.
- Если DataLens будут использовать, понадобятся: роль БД только на чтение, схема или набор
  опубликованных представлений для BI, описание в `docs/architecture/overview.md` (внешние
  системы) и, при выборе варианта развёртывания, отдельный ADR.
- Реализация Offer Analytics включает контрольную точку п. 2 и запись её результата.
- Открытые вопросы: Q-GEN-10 (свой BI или внешний), Q-GEN-12 (вариант DataLens, доступ,
  передача данных).
