# ADR-0003: Хранение данных и истории

- Статус: Принят
- Дата: 2026-09-15
- Уточнён: 2026-09-15 — модель истории лота, [ADR-0007](0007-lot-history-model.md) (см. «История изменений»)

## Контекст

- Нужны текущие данные и их изменения во времени: «дата первого обнаружения», «дата
  последнего обновления», «изменение цены за день, неделю, месяц и квартал» (ТЗ п. 3),
  ежемесячные срезы деклараций (ТЗ п. 6).
- По каждому лоту требуются URL и скриншот (ТЗ п. 3), то есть доказательство наблюдения.
- Источники ненадёжны: вёрстка меняется, парсеры ошибаются. Нужна возможность
  переобработать сырые данные и найти причину неверного значения.
- Аналитика — агрегаты, медианы, распределения, сравнения по многим измерениям.
- Модули должны развиваться независимо и не ломать данные друг друга.
- Ожидаемый объём — см. [A-04](../requirements/assumptions.md).

## Решение

### 1. Одна база PostgreSQL, схема на модуль

- Каждый модуль владеет своей схемой: `core`, `offeranalytics`, `collection`,
  `declarations`, `floorplans`, `benchmark`, `location`.
- **Писать в схему может только модуль-владелец.**
- Другие модули читают чужие данные через публичный API модуля (Go) или через
  **представления (views), явно опубликованные владельцем** как контракт чтения.
  Опубликованные представления документируются в документации модуля. Прямые запросы к
  чужим таблицам запрещены.
- Внешние ключи из таблиц модуля на идентификаторы Core разрешены: Core — стабильное ядро,
  от публичных контрактов которого модули зависят по умолчанию. Внешние ключи между
  некорневыми модулями запрещены, пока зависимость между этими модулями не разрешена
  отдельным ADR ([ADR-0004](0004-module-boundaries.md)).
- Данные хранятся в схеме модуля, отвечающего за них по доменной ответственности. Результаты
  других модулей (анализ планировок, локация, оценки продукта) не переносятся в `core`
  ради обмена между модулями (ADR-0004).
- Схема `public` не используется для бизнес-таблиц (там только служебная таблица версий goose).

### 2. История: наблюдения + версии при изменении

- **Наблюдение (observation)** — неизменяемый факт «что источник показал в момент T» с
  привязкой к запуску сбора и доказательствам. Хранится в `collection`.
- **Версия состояния лота** — в `core`: новая запись создаётся **только при изменении**
  значимых атрибутов (цена, статус, скидка, условия…). Интервал действия задаётся полями
  `valid_from` / `valid_to` (SCD Type 2). Текущее состояние — версия с `valid_to IS NULL`
  (или отдельная таблица текущего состояния, решается при проектировании Core).
- Даты первого обнаружения и последнего подтверждения лота хранятся явно. Последнее
  подтверждение обновляется при каждом наблюдении, даже без изменений.
- **Производные показатели** (агрегаты Offer Analytics, расчёты деклараций) можно
  пересчитать из исходных данных. Материализуются только при необходимости и только в схеме
  своего модуля.
- **Срезы деклараций** — неизменяемые снимки на отчётную дату.

### 3. Файлы вне БД

Скриншоты, PDF, изображения планировок, сырые HTML/JSON-ответы хранятся в файловом
хранилище за портом (локальная ФС → S3-совместимое). В БД хранятся метаданные: ключ
объекта, тип, размер, контрольная сумма, время получения, источник.

### 4. Соглашения по схеме

| Аспект | Соглашение |
|---|---|
| Имена | `snake_case`, таблицы во множественном числе (`lots`, `lot_versions`) |
| Первичные ключи | `uuid`, генерируются приложением (UUIDv7 — упорядочены по времени, удобны для индексов и слияния данных) |
| Время | `timestamptz` в UTC; бизнес-даты (дата среза) — `date` |
| Деньги | `numeric(15,2)`, рубли; без `float` |
| Площади | `numeric(10,2)`, м² |
| Перечисления | `text` + `CHECK` или таблица-справочник; не `enum`-тип PostgreSQL (его сложно менять миграциями) |
| Сырые/полуструктурированные данные | `jsonb`, только там, где структура действительно переменная |
| Служебные поля | `created_at`, `updated_at` для изменяемых таблиц; неизменяемые таблицы без `updated_at` |

### 5. Миграции

- goose, SQL-файлы в `migrations/`, одна последовательность для всех модулей.
- Имя: `<UTC YYYYMMDDHHMMSS>_<module>_<описание>.sql`. Метка времени уменьшает конфликты
  при параллельной работе над модулями.
- Каждая миграция содержит `Up` и `Down`. Применённая миграция не редактируется: исправление
  делается новой миграцией.
- Миграция модуля затрагивает только схему этого модуля (исключение — создание расширений,
  например `postgis`, с пояснением).
- Интеграционный тест проверяет `up → down до 0 → up`.

### 6. Масштабирование (когда понадобится, не сейчас)

- Партиционирование по времени (помесячно) таблиц наблюдений и версий — при росте объёма.
- Материализованные представления или витрины для тяжёлых срезов Offer Analytics.
- PostGIS включается миграцией модуля Location. Образ в Docker Compose его уже содержит.

## Обоснование

- Одна СУБД покрывает реляционную модель, аналитику, JSONB, партиционирование и гео — это
  минимальная инфраструктура ([ADR-0002](0002-tech-stack.md)).
- Схема на модуль делает владение данными видимым в БД и позволяет в будущем вынести модуль
  без распутывания таблиц.
- Разделение «наблюдения / версии» даёт и доказательность (что и когда показал источник),
  и компактную историю для аналитики (строки только при изменении).
- Хранение файлов вне БД не раздувает базу и резервные копии.

## Рассмотренные альтернативы

| Вариант | Почему отказались |
|---|---|
| Полный ежедневный снимок всех лотов | Простой, но объём растёт линейно по дням при малом числе изменений; «первое обнаружение» и изменения всё равно приходится вычислять |
| Только текущее состояние + журнал изменений (audit log) в JSON | Сложные запросы «цена на дату X» и динамика по периодам |
| Event sourcing | Избыточная сложность для аналитического инструмента |
| ClickHouse / TimescaleDB для истории и аналитики | Дополнительный компонент без подтверждённой необходимости при A-04; можно добавить позже как витрину |
| База данных на модуль | Нужны межбазовые запросы для аналитики; больше эксплуатации |
| Одна схема `public` для всех | Невидимое владение данными, конфликты имён, модули легко срастаются через JOIN |
| `bigint identity` ключи | Хорошо для одной БД, но UUID удобнее для приёма данных из разных источников и генерации ID до вставки; выбран UUIDv7 ради упорядоченности |

## Последствия

- Проектирование Core (Module 1) должно включать модель версий лота, правило «значимого
  изменения» и контракт ingestion API.
- Offer Analytics зависит от опубликованных представлений Core. Их набор определяется при
  реализации Core и Offer Analytics.
- Перед реализацией Data Collection нужен порт файлового хранилища в `platform` и ответ на
  Q-GEN-08 (сроки хранения).
- Дисциплина «пишет только владелец» проверяется ревью. Автоматическая проверка SQL
  (например, разные роли БД на модуль) — возможное улучшение позже.
