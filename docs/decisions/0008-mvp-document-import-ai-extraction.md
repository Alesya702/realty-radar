# ADR-0008: Импорт PDF с AI-извлечением в MVP — компонент Data Collection

- Статус: Принят
- Дата: 2026-09-15
- Уточняет: [ADR-0002](0002-tech-stack.md) (строка «OCR/CV/ML планировок»),
  [ADR-0004](0004-module-boundaries.md) (границы Data Collection и Floor Plans)
- Связан: [ADR-0006](0006-core-identity-and-source-references.md),
  [ADR-0007](0007-lot-history-model.md), [pdf-extraction.md](../architecture/pdf-extraction.md)

## Контекст

- [уточнение 2026-09-15, решение по scope MVP] Автоматический сбор с сайтов конкурентов не входит
  в MVP. Он остаётся будущим источником: без парсеров, browser automation и инфраструктуры ради
  scraping. Основной автоматизированный способ получения данных из неструктурированного источника в
  MVP — PDF: «PDF → AI-извлечение → стандартный JSON → валидация → проверка пользователем →
  исправление → подтверждённый импорт → Core». Ручной ввод остаётся.
- MVP проверяет гипотезу: можно ли multimodal AI / Vision преобразовывать разнородные PDF в
  стандартное представление Realty Radar. Формат PDF не фиксирован, AI-провайдер не выбран и
  должен быть заменяемым.
- ТЗ: п. 1 — «извлечение данных из PDF», «распознавание площадей и подписей помещений»; п. 3 —
  данные лота; п. 4 — документы проекта как источники.
- Текущие документы относят распознавание к Floor Plans: ADR-0002 («OCR/CV/ML планировок — порт
  в модуле Floor Plans»), A-17, `modules.md` п. 3.5 («приём изображений и PDF», «помещения и их
  площади и подписи»). PDF в MVP — универсальный источник: проект, корпуса, лоты, цены, иногда
  планировки.
- `modules.md` п. 3.3 уже относит к Data Collection «импорт файлов и ручные загрузки»,
  «получение документов проекта как файлов», нормализацию и передачу данных в Core.
- Core не должен читать PDF, вызывать LLM, выполнять OCR, знать провайдера, содержать промпты,
  анализировать изображения, хранить результаты анализа планировок.

## Решение

1. **PDF Import / AI Extraction — компонент модуля Data Collection.** Новый бизнес-модуль не
   создаётся.
2. **Разделение ответственности:**
   - **извлечение фактов из документов** (явно присутствующих значений) — Data Collection;
   - **анализ планировок** (коэффициенты, типизация помещений, классификация, мастер-спальни,
     проходные помещения, мокрые зоны, похожие планировки) — Floor Plan Analysis, как прежде.
3. **AI-провайдер — порт `DocumentExtractor`** в `collection/internal/app`, адаптеры — в
   `collection/internal/adapters/extraction/<provider>/`. Промпты, растеризация страниц и
   особенности провайдера — только в адаптере. Выбор провайдера — отдельный ADR после ответов
   Q-GEN-11 и Q-PDF-02.
4. **Extraction Result** — стандартный JSON с версией схемы, принадлежит Collection
   (`collection`, jsonb). Это **предварительный** результат, не данные Core и не контракт Core.
5. **Проверка и подтверждение пользователем обязательны** в MVP. Решения пользователя хранятся
   отдельно от неизменяемого Extraction Result; подтверждённый импорт неизменяем.
6. **В Core поступают только подтверждённые нормализованные данные** — через
   `IngestObservationBatch` (тот же контракт — для ручного ввода и будущего автоматического сбора)
   и команды Core (создание проекта). Сопоставление — через запросы Core (ADR-0006).
7. **Факты о планировках и помещениях из PDF не передаются в Core.** До реализации Floor Plans они
   хранятся в Collection. Способ передачи в Floor Plans выбирается отдельным ADR по ADR-0004 при
   реализации Floor Plans; сейчас межмодульная зависимость не добавляется.
8. **Файлы — через порт файлового хранилища в `platform`** (направление ADR-0002/ADR-0003:
   локальная ФС → S3-совместимое); PDF-импорт — первый потребитель. Фоновое извлечение — очередь
   задач на PostgreSQL по направлению ADR-0002 (библиотека выбирается при реализации).
9. **Автоматический сбор с сайтов — future scope** в том же модуле Data Collection. Для него
   сейчас ничего не создаётся.

## Обоснование

- Collection уже владеет входным контуром «внешний источник → нормализация → Core». PDF — ещё
  один внешний источник. Один владелец входа в Core исключает второй путь записи.
- PDF в MVP несёт данные лотов и проектов. Размещение в Floor Plans сделало бы анализ планировок
  поставщиком цен и статусов для Core и смешало бы две ответственности.
- Новый модуль повторил бы ответственность Collection без доменной причины (ADR-0001, ADR-0004).
- Порт провайдера и стандартный JSON делают провайдера заменяемым: меняется адаптер, а формат,
  проверка и Core остаются.
- Проверка пользователем и изоляция Extraction Result не дают неподтверждённым результатам AI
  попасть в канонические данные.

## Рассмотренные альтернативы

| Вариант | Почему отказались |
|---|---|
| Floor Plan Analysis как владелец PDF-импорта | PDF — универсальный источник; анализ смешался бы с получением данных лотов |
| Новый модуль Documents / Import | Дублирует Collection; +1 модуль без доменной причины. Возможно позже отдельным ADR, если импорт документов разрастётся (декларации, документы для Benchmark) |
| AI-извлечение в Core | Нарушает независимость Core от способа получения данных |
| Автоматическая запись результата AI в Core | Неподтверждённые данные в истории; противоречит постановке MVP |
| Собственный OCR/CV-алгоритм | Противоречит гипотезе MVP; дорого без подтверждённой потребности |
| Выбрать провайдера сейчас | Нет ответа о допустимости передачи документов (Q-GEN-11) и реальных PDF для сравнения |
| Универсальный формат сырых данных для PDF и будущих сайтов | Преждевременно; общий только входной контракт Core |

## Последствия

- Описание Data Collection и Floor Plans в `modules.md` и ADR-0002 уточняется после принятия:
  Collection — «импорт документов и AI-извлечение фактов», Floor Plans — «анализ планировок»;
  OCR/CV/ML для анализа планировок остаётся портом Floor Plans. A-17 уточняется.
- Появляются первые потребители порта файлового хранилища и фоновых задач (при реализации).
- Выбор AI-провайдера — отдельный ADR; до реализации нужны ответы Q-GEN-11 и Q-PDF-02 и набор
  реальных PDF (Q-PDF-01, Q-PDF-10).
- При реализации Floor Plans понадобится ADR о передаче фактов планировок из Collection
  (сценарий уже упомянут в ADR-0004 п. 4).
- В MVP частота и полнота истории цен зависят от загружаемых PDF. Показатели ТЗ п. 3 «изменение за
  день» могут быть недостижимы до автоматического сбора (отражено в scope.md).
- Если MVP не подтвердит гипотезу, меняется только компонент Collection; Core не затрагивается.
