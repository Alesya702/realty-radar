# ADR-0001: Модульный монолит

- Статус: Принят
- Дата: 2026-09-15

## Контекст

По ТЗ в системе семь функциональных областей: доменная модель проектов и лотов, аналитика
предложения, сбор данных, декларации, планировки, продуктовый бенчмарк, локация. Области
будут реализовываться последовательно, частично разными людьми (и сессиями Claude Code),
а затем проект может перейти к классической команде.

Ограничения и силы:

- требования — первый драфт, границы областей ещё будут уточняться;
- все области опираются на одни и те же сущности (проект, корпус, лот);
- аналитика требует тяжёлых запросов по общим данным;
- внутренний инструмент, небольшое число пользователей, скромная команда
  ([assumptions A-01, A-03](../requirements/assumptions.md));
- при этом у областей разный характер нагрузки: сбор (сеть, долгие задачи), распознавание
  планировок (CPU, возможно ML), аналитика (БД).

## Решение

Строим **одно приложение на Go (один бинарник, один деплой, одна БД PostgreSQL)**, разделённое
на бизнес-модули с явными границами:

- модули — `src/modules/<module>`, публичный API — корневой пакет, внутренности —
  `internal/` (закрыты компилятором);
- Core — центральный модуль; остальные модули по умолчанию зависят только от публичных
  контрактов Core, прямые связи между ними — только по отдельному ADR (политика — в
  [ADR-0004](0004-module-boundaries.md));
- внешние интеграции, парсеры и AI/ML — адаптеры за портами модулей;
- связывание модулей — только в composition root `src/app`;
- правила зависимостей проверяет тест `tests/architecture`.

Выделение модуля или компонента в отдельный процесс возможно позже, отдельным ADR, если
появится конкретная причина. Например, отдельный воркер сбора или сервис распознавания
планировок на другом стеке.

## Обоснование

- Один деплой и одна БД — минимальная операционная сложность для внутреннего инструмента.
- Транзакции, JOIN и отчёты по общим данным без распределённых согласований.
- Рефакторинг границ, пока требования уточняются, дешевле внутри одного репозитория и процесса.
- Явные границы и автоматическая проверка зависимостей сохраняют возможность позже вынести
  модуль в отдельный сервис.
- Структура понятна классическим разработчикам и удобна для пошаговой работы в Claude Code:
  один модуль — один этап.

## Рассмотренные альтернативы

| Вариант | Почему отказались |
|---|---|
| Микросервисы (сервис на модуль) | Сетевые контракты, распределённые данные, отдельные деплои и наблюдаемость без реальной потребности в независимом масштабировании; дорого менять границы при сыром ТЗ |
| Классический монолит без модулей (слои `handlers/services/repositories` на всё приложение) | Быстрый старт, но бизнес-логика областей перемешивается, парсеры срастаются с доменом, модули нельзя развивать независимо |
| Монолит + отдельные сервисы сразу для сбора и ML | Преждевременно: неизвестны объёмы, источники и ML-подход (Q-GEN-04, Q-PLAN-09) |
| Отдельные Go-модули (`go.mod`) или репозитории на каждый модуль | Версионирование и согласование изменений между модулями без выгоды на этой стадии |

## Последствия

- (+) Простой запуск: `go run` + PostgreSQL.
- (+) Модули реализуются по этапам, начиная с Core.
- (−) Все модули масштабируются вместе. Тяжёлые фоновые задачи (сбор, распознавание) могут
  конкурировать с веб-запросами за ресурсы. Это смягчается запуском того же бинарника в
  разных ролях (например, `serve` и будущий `worker`), не отказываясь от монолита.
- (−) Дисциплина границ держится на соглашениях, `internal/` и архитектурном тесте. Нарушения
  нужно исправлять, а не добавлять исключения в тест.
- (−) Если распознавание планировок потребует Python-стека, это будет первый кандидат на
  отдельный процесс (решается отдельным ADR).
