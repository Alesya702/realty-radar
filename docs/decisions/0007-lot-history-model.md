# ADR-0007: Модель истории лота: размещения, пакеты приёма, версии и присутствие

- Статус: Принят
- Дата: 2026-09-15 (редакция 2, принята 2026-09-15; см. «История изменений»)
- Уточняет: [ADR-0003](0003-data-storage.md), п. 2 «История: наблюдения +
  версии при изменении»
- Связан: [ADR-0006](0006-core-identity-and-source-references.md),
  [ADR-0008](0008-mvp-document-import-ai-extraction.md),
  [core-domain-model.md](../architecture/core-domain-model.md) (п. 8, 9.4)

## Контекст

ADR-0003 задал подход: неизменяемые наблюдения в `collection`, версии состояния лота в `core`
с `valid_from`/`valid_to`, явные даты первого и последнего подтверждения. Детальная модель
оставлена проектированию Core. При проектировании выявлено:

1. **Отсутствие лота неоднозначно** [уточнение 2026-09-15]: не показан, снят с продажи, источник
   недоступен, ошибка извлечения, скрыт забронированный лот. Отсутствие не означает «продан».
2. **Несколько источников** на лот: запись только «победившего» значения делает выбор
   необратимым, а правило приоритета не задано (Q-CORE-18).
3. [уточнение 2026-09-15] **В MVP данные поступают из PDF**, подтверждённых пользователем:
   - наблюдения редкие и нерегулярные;
   - документ может быть старше уже загруженного, и повторный импорт старого PDF — нормальный
     сценарий;
   - документ обычно не перечисляет все лоты;
   - дата актуальности данных может отличаться от даты загрузки;
   - в документе часто просто нет части сведений (скидок, отделки). Это не значит, что их нет у
     лота.
4. Требуемые запросы: состояние и цена на дату, изменение цены, появление и исчезновение скидки,
   смена статуса, исчезновение и повторное появление лота.

## Решение

1. **Наблюдения и промежуточные данные остаются в Data Collection** (как в ADR-0003; для PDF —
   документ, Extraction Result, подтверждённый импорт). Core их не хранит.
2. **Пакет приёма `IngestionBatch` в Core** — заголовок каждой порции подтверждённых данных:
   источник; способ поступления (`document_import`, `manual_entry`, `automated_collection`);
   идемпотентная ссылка на импорт или запуск в Collection (без FK); **момент данных** и его
   основание (`document_date`, `received_date`, `upload_time`, `entry_time`, `collection_time`);
   **область** (проект, корпус?, типы лотов); **полнота** (`complete` / `partial`); момент
   подтверждения.
3. **История ведётся на уровне размещения** (лот × источник, ADR-0006): `LotListingVersion` с
   интервалом `[valid_from, valid_to)` и **`last_observed_at`** — моментом последнего
   наблюдения, подтвердившего значения. Одна текущая версия (`valid_to IS NULL`), интервалы без
   разрывов.
4. **Каноническое состояние лота — проекция** версий основного размещения. Отдельной таблицы
   текущего состояния нет.
5. **Присутствие (`listed` / `delisted`) отделено от статуса продаж.** «Продан» и «снят» — только
   из явных сведений источника.
6. **Отсутствие учитывается только** в `complete`-пакете, для размещений того же источника в
   области, если момент пакета не раньше текущей версии, после порога промахов (Q-CORE-17). Для
   документов по умолчанию `partial`; `complete` утверждает пользователь.
7. **Трёхзначное состояние поля в наблюдении:** `value`; `unknown` — значение не меняется;
   `absent` — источник явно показывает отсутствие, значение очищается.
8. **Новая версия** — при изменении присутствия, статуса, площади, комнатности и формата, отделки,
   видов, особенностей, цены, цены до скидки, признака акции. Подтверждение без изменений
   обновляет `last_observed_at`. URL, дата публикации, внешний ключ и размещение лота версию не
   создают.
9. **Неупорядоченные наблюдения применяются вставкой в историю:** расширение первой версии назад;
   деление версии, если момент позже её последнего подтверждения; обновление `last_observed_at`
   при равенстве. **Противоречие с более поздним подтверждением отклоняется** (`history_conflict`)
   и не перезаписывает историю.
10. **`valid_from` — момент данных** пакета; модель не битемпоральная.
11. **`first_seen_at` / `last_seen_at`** размещения — минимум и максимум моментов положительных
    наблюдений; для лота вычисляются.
12. **Пакет применяется атомарно и идемпотентно.** Исправление ошибочно подтверждённых данных —
    замена значений версий, созданных пакетом, без новой версии (`CorrectBatchData`). Полный отзыв
    с переигрыванием — позже (Q-CORE-27, Q-PDF-11).
13. История атрибутов структурных сущностей этим решением не ведётся.

## Обоснование

- Момент данных с основанием отделяет «когда данные были актуальны» от «когда их загрузили».
  Для PDF это разные даты.
- `last_observed_at` делает явной давность знания: при редких документах интервал версии может
  тянуться месяцами без подтверждения. Аналитика должна это видеть.
- Вставка неупорядоченных наблюдений нужна для импорта старых документов. Отклонение
  противоречий с более поздними подтверждениями — простое правило, которое не требует хранить в
  Core все наблюдения.
- `unknown` ≠ `absent` защищает историю: документ без раздела скидок не «отменяет» скидку.
- Полнота и область — минимальная информация, чтобы отличать «исчез» от «не упомянут».
- История на уровне размещения ничего не теряет при противоречиях источников; правило выбора
  канонического источника применяется при чтении.
- Один механизм обслуживает PDF, ручной ввод и будущий автоматический сбор.

## Рассмотренные альтернативы

| Вариант | Почему отказались |
|---|---|
| Версии на уровне канонического лота (буквально ADR-0003) | Необратимый выбор значения при нескольких источниках |
| Отклонять наблюдения старше текущей версии (редакция 1) | Импорт старого PDF — нормальный сценарий MVP |
| Хранить в Core все наблюдения и пересчитывать версии | Дублирует Collection; объём при будущем сборе (ADR-0003 отклонил полные снимки) |
| Пустое значение в наблюдении = значение исчезло | Любой неполный документ стирал бы известные сведения |
| Отсутствие в любом документе / результате → «продан» | Противоречит требованию; ложные продажи |
| `delisted` как значение статуса продаж | Смешивает факт источника и вывод системы |
| Дата загрузки как момент данных | Искажает историю цен при загрузке документа, выпущенного раньше |
| Битемпоральная модель | Нет требования «что система знала на дату» |
| Полевой провенанс и аудит в Core | Избыточно для MVP; решения по полям хранятся в Collection |

## Последствия

- Входной контракт Core (`IngestObservationBatch`) несёт момент данных, основание, область,
  полноту и трёхзначные поля. Collection отвечает за корректное заполнение, пользователь — за
  подтверждение для документов.
- Запросы «на дату» фильтруют по `presence` и отдают `last_observed_at`.
- Порог промахов, конвенция «на дату», основание даты для PDF — параметры, ожидающие ответов
  (Q-CORE-17, Q-CORE-26, Q-PDF-03).
- Смена основного размещения ретроспективно меняет каноническую историю лота.
- После принятия ADR-0003 получает отметку «Уточнён» со ссылкой на этот ADR.
- Поддержка агрегаторов с несколькими объявлениями на лот (Q-CORE-14) может потребовать
  пересмотра единицы истории.
