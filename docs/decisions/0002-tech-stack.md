# ADR-0002: Технологический стек

- Статус: Принят
- Дата: 2026-09-15
- Уточнён: 2026-09-15 — статус выбора Go, UI для MVP; AI-извлечение из PDF — [ADR-0008](0008-mvp-document-import-ai-extraction.md); sqlc не подключён в Core MVP (см. «История изменений»)

## Контекст

Исходное бизнес-ТЗ не задаёт язык и технологии реализации. Выбор языка — техническое
решение этого ADR (см. строку «Язык» ниже), а не требование бизнеса.

Требования и факторы, влияющие на стек:

- веб-интерфейс с аналитическими таблицами, фильтрами и графиками;
- потенциально большой объём лотов и история изменений;
- фоновые задачи (ежедневный сбор, ежемесячная выгрузка деклараций, пересчёты);
- будущий scraping, обработка PDF, AI/CV-анализ планировок, геоданные и внешние API;
- локальный запуск без сложной инфраструктуры;
- удобство разработки через Claude Code и последующая передача классическим разработчикам.

Принцип: для каждого будущего требования выбираем направление, но **добавляем компонент в
проект, только когда появляется первый реальный потребитель**.

## Решение

### Используется сейчас (в каркасе)

| Область | Выбор | Почему | Альтернативы | Ограничения |
|---|---|---|---|---|
| Язык | Go 1.27 — **принятое техническое решение** | Один статический бинарник и простой деплой; простая конкурентность для сбора данных; строгая типизация и стандартная структура проекта облегчают передачу разработчикам и работу через Claude Code | Python (Django/FastAPI) — сильнее для scraping, PDF и ML, но слабее типизация и сложнее деплой; TypeScript/Node.js — один язык для фронтенда и бэкенда; Java/Kotlin, C# — тяжелее для небольшого внутреннего инструмента | Слабая экосистема для CV/ML и работы с PDF (см. ниже) |
| HTTP | стандартный `net/http`, `ServeMux` с шаблонами маршрутов (метод + путь) | Без зависимостей; возможностей роутера достаточно; стандарт знаком любому Go-разработчику | chi, echo, gin | Нет готовых middleware — пишем минимальные сами (`platform/httpserver`) |
| СУБД | PostgreSQL 17 | Реляционная модель рынка, оконные функции и агрегаты для аналитики, партиционирование для истории, JSONB для сырых данных, PostGIS для гео — всё в одной СУБД | MySQL, ClickHouse, MongoDB — см. ADR-0003 | Для очень тяжёлой OLAP-аналитики может понадобиться колоночное хранилище (не ожидается при A-04) |
| Драйвер БД | pgx v5 (`pgxpool`) | Самый производительный и полный драйвер PostgreSQL для Go: типы PG, `COPY` для массовой загрузки, пул | `database/sql` + lib/pq (lib/pq в режиме поддержки) | Специфичен для PostgreSQL — это осознанно |
| Миграции | goose v3, SQL-файлы, встроены в бинарник (`embed`) | Простые SQL-миграции с Up/Down; запуск из того же бинарника (`realtyradar migrate up`); не нужен отдельный CLI | golang-migrate (две отдельные up/down-файла, менее удобен как библиотека), Atlas (декларативный, мощнее, но сложнее и частично коммерческий), tern | Одна таблица версий на все модули; миграции должны вручную соблюдать владение схемами |
| Конфигурация | переменные окружения `RR_*`, небольшой собственный загрузчик; `.env` через godotenv только для локальной разработки | 12-factor, работает одинаково в Docker, CI и локально; все ошибки конфигурации выводятся сразу | viper, koanf, envconfig | Нет файлов конфигурации — пока не нужны |
| Логирование | `log/slog` (text локально, JSON в production) | Стандартная библиотека, структурированные логи | zap, zerolog | — |
| UI | серверный рендеринг: `html/template`, шаблоны встроены в бинарник | Один язык и один деплой; для внутреннего аналитического инструмента не нужен отдельный фронтенд-проект и сборка | SPA (React/Vue + TypeScript) с JSON API | Сложные интерактивные таблицы требуют аккуратной работы с JS-библиотеками (см. планируемое). Уточнено в [ADR-0005](0005-ui-approach-and-bi.md): SSR + htmx — решение для MVP с контрольной точкой при реализации Offer Analytics |
| Тесты | стандартный `testing`, `httptest`; интеграционные тесты на реальном PostgreSQL (build tag `integration`); архитектурный тест зависимостей | Без лишних зависимостей; интеграция проверяет реальные SQL и миграции | testify, testcontainers-go | testcontainers не используется: требует Docker, а он доступен не везде (например, на машине, где создавался каркас). База для тестов задаётся через `RR_TEST_DATABASE_URL` |
| Локальная инфраструктура | Docker Compose: `postgis/postgis:17-3.5` | Одна команда для БД; образ уже содержит PostGIS для будущего модуля Location | Нативная установка PostgreSQL | Docker нужен только для БД; приложение запускается через `go run` |
| CI | GitHub Actions: gofmt, vet, unit, архитектурные и интеграционные тесты (сервис PostgreSQL), сборка | Стандартный вариант | GitLab CI и др. — при другом хостинге | Хостинг репозитория не определён (A-06); файл легко перенести |

## Обоснование

Стек минимален: стандартная библиотека Go + три зависимости (pgx, goose, godotenv) +
PostgreSQL. Всё запускается локально одной командой для БД и `go run`. Решения
общепринятые и хорошо документированы, поэтому их легко поддерживать разработчикам без
знания проекта и эффективно использовать Claude Code. Требования будущих модулей закрываются
возможностями PostgreSQL (JSONB, партиционирование, PostGIS) и подключаемыми адаптерами без
заранее добавленной инфраструктуры.

## Рассмотренные альтернативы (ключевые)

- **SPA-фронтенд (React + TypeScript) с самого начала.** Даёт богатые интерактивные таблицы, но
  добавляет второй язык, сборку, отдельный деплой и дублирование валидации. Для внутреннего
  BI с фильтрами серверного рендеринга с htmx достаточно. JSON API модулей оставляет путь к
  SPA открытым.
- **Готовый BI (Metabase, Superset, DataLens) поверх PostgreSQL вместо своего UI для
  аналитики.** Может резко ускорить п. 2 ТЗ. Решение за бизнесом (Q-GEN-10). Архитектура
  не препятствует: аналитические представления в PostgreSQL можно подключить к внешнему BI.
  Возможность использования DataLens и условия подключения зафиксированы в
  [ADR-0005](0005-ui-approach-and-bi.md).
- **ORM (GORM/ent).** Аналитика — это в основном SQL с агрегатами и оконными функциями. ORM
  здесь мешает больше, чем помогает. Выбран SQL-first подход (pgx сейчас, sqlc — с Core).
- **Redis для очередей и кэша.** Лишний компонент при масштабе A-04. Очередь на PostgreSQL
  проще и транзакционна.

## Последствия

- Локально нужны Go 1.27+ и PostgreSQL 17 (Docker Compose или нативная установка).
- Для ML-части, скорее всего, придётся принять исключение из «только Go» — это решается
  отдельным ADR при реализации Floor Plans. До этого распознавание скрыто за портом модуля.
- Добавление каждого компонента из «направлений» сопровождается обновлением README,
  CLAUDE.md, `.env.example` и, если компонент существенный (очередь, хранилище, ML-сервис),
  отдельным ADR.
