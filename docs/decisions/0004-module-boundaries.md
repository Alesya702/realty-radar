# ADR-0004: Границы модулей и правила зависимостей

- Статус: Принят (граница Offer Analytics ожидает подтверждения бизнеса — Q-STR-02)
- Дата: 2026-09-15
- Уточнён: 2026-09-15 — политика межмодульных зависимостей; граница Data Collection и Floor Plans ([ADR-0008](0008-mvp-document-import-ai-extraction.md)) (см. «История изменений»)

## Контекст

Предварительная декомпозиция задала 7 модулей: Core / Projects & Lots, Apartment Mix
Analytics, Data Collection, Project Declarations, Floor Plan Analysis, Product Benchmark,
Location Analytics. При сверке с ТЗ обнаружено:

1. **Ценовая аналитика (ТЗ п. 3, «Ценовые показатели»)** — большой блок требований (min,
   avg, median, цены по разрезам, премии, динамика, эффект акций, рассрочка, сравнение с
   конкурентами). В предварительной декомпозиции ему нет модуля. Data Collection только
   получает цены, Core хранит их историю, а расчёт показателей не относится ни к одному из
   них.
2. **Таблица «Обязательные показатели»** находится в п. 1 (планировки), но по содержанию —
   это показатели структуры предложения и цен.
3. **Определение конкурентов** (классы, прямые/косвенные/референсные) находится в п. 1, но
   относится к модели проектов.

## Решение

### 1. Состав модулей

Сохраняем 7 модулей и уточняем одну границу:

- Модуль 2 называется **Offer Analytics (Apartment Mix & Prices)**, пакет `offeranalytics`.
  Он включает квартирографию (п. 2), обязательные показатели (таблица п. 1) и ценовые
  показатели (п. 3).
- Конкуренты и классы проектов относятся к **Core**.
- Остальные границы — как в предварительной декомпозиции. Детали — в
  [modules.md](../architecture/modules.md).

### 2. Политика межмодульных зависимостей

```
offeranalytics ─┐
collection ─────┤
declarations ───┼──► публичные контракты core      (разрешено по умолчанию)
floorplans ─────┤
benchmark ──────┤
location ───────┘

<модуль A> ──► публичный контракт <модуля B>       (только по отдельному ADR
                                                    + разрешение в архитектурном тесте)
```

1. **Core не зависит от остальных бизнес-модулей.**
2. **Некорневые модули по умолчанию могут зависеть только от публичных контрактов Core.**
   Публичный контракт — корневой пакет `src/modules/core` и опубликованные Core
   представления для чтения ([ADR-0003](0003-data-storage.md)). Внутренние пакеты и таблицы
   Core контрактом не являются.
3. **Прямая зависимость между некорневыми модулями допускается только при реальной
   бизнес-необходимости.** Её нужно явно зафиксировать отдельным ADR и разрешить в
   архитектурном тесте (`allowedModuleDeps` в `tests/architecture/dependencies_test.go`, с
   комментарием-ссылкой на ADR). Такая зависимость тоже идёт только через публичный контракт
   модуля-поставщика и не должна создавать циклов.
4. **Данные не переносятся в Core исключительно для обмена между другими модулями.** Core
   хранит только данные своей доменной ответственности. Каждый модуль хранит результаты своей
   работы у себя:

   | Данные | Владелец |
   |---|---|
   | базовые характеристики Project / Lot (площадь, этаж, комнатность, цена, статус и т. п.) | Core |
   | результаты анализа планировок (помещения, коэффициенты, классификация, евроформат по планировке) | Floor Plans |
   | рассчитанные характеристики локации (POI, расстояния, время в пути, барьеры) | Location |
   | оценки продукта | Benchmark |

   Другие модули ссылаются на сущности Core по идентификаторам, но не записывают свои
   результаты в Core.
5. **Любая новая межмодульная зависимость требует ADR и изменения архитектурного теста.**
   Это правило не меняется.

Если модулю в будущем понадобятся данные нескольких модулей, рассматриваются варианты:

- явная межмодульная зависимость через публичный контракт (п. 3);
- read model / reporting model — модель для чтения, собранная из опубликованных контрактов
  модулей-владельцев;
- отдельный агрегирующий модуль, который зависит от нескольких модулей.

**Выбор делается только при появлении конкретного сценария** и оформляется ADR. Такая
инфраструктура заранее не проектируется и не создаётся.

### 3. Технические правила границ

- Модуль используется только через корневой пакет `src/modules/<module>`. Реализация лежит
  в `src/modules/<module>/internal/...`, и компилятор Go запрещает импорт этих пакетов из
  других модулей.
- Внутри модуля: `internal/domain` не зависит от инфраструктуры (`platform`, `web`,
  `net/http`, `database/sql`, pgx) и от `app`/`adapters` своего модуля.
- `platform` не зависит от модулей, `web` и `app`. `web` не зависит от модулей и `app`.
  Модули не зависят от `app`.
- Коллекторы и парсеры живут только в Data Collection
  (`collection/internal/adapters/sources/...`) и передают данные в Core через его
  публичный ingestion API.

### 4. Возможные будущие межмодульные связи (не разрешены, не проектируются заранее)

Это не план реализации, а известные из ТЗ места, где вопрос может возникнуть. Вариант
выбирается по п. 2 при появлении конкретного сценария.

| Потребитель ← поставщик | Возможный сценарий | Ограничение уже сейчас |
|---|---|---|
| Offer Analytics ← Floor Plans | срезы по евроформату или типу планировки, определённым анализом планировок | результаты анализа не копируются в Core; евроформат, указанный источником как базовый атрибут лота, — данные Core (Q-OFFER-03) |
| Offer Analytics ← Declarations | сверка остатков с лотами (Q-DECL-06) | после ответа бизнеса |
| Benchmark ← Location | общий scoring проекта | после появления правил scoring |
| Floor Plans / Benchmark ← Collection | использование документов и изображений, полученных сбором | файлы и ссылки на них не переносятся в Core ради обмена |

## Обоснование

- Ценовые показатели и квартирография считаются по одним данным (лоты и их версии в Core),
  одинаковым механизмом срезов (класс, девелопер, район, корпус, тип, площадь, этаж, отделка,
  вид, срок) и показываются в одном BI-интерфейсе (п. 2). Разделение дало бы два модуля с
  одинаковыми измерениями и фильтрами.
- Звезда зависимостей вокруг Core по умолчанию исключает циклы и позволяет реализовать и
  тестировать модули в любом порядке после Core.
- Абсолютный запрет связей между некорневыми модулями подталкивал бы к переносу чужих данных
  в Core ради обмена. Core превратился бы в «общую свалку» без ясной ответственности. Поэтому
  связь разрешается точечно, через ADR и тест, а владение данными остаётся у модуля, который
  их создаёт.
- `internal/` + архитектурный тест дают проверку границ компилятором и CI, а не только
  соглашением.

## Рассмотренные альтернативы

| Вариант | Почему отказались |
|---|---|
| Отдельный 8-й модуль Pricing Analytics | Дублирует измерения, фильтры и UI квартирографии. Остаётся возможным разделением позже, если модуль разрастётся |
| Ценовые показатели в Core | Смешивает каноническую модель и аналитику, раздувает центральный модуль |
| Ценовые показатели в Data Collection | Смешивает получение данных и анализ; противоречит отделению коллекторов |
| Модуль-пакет без `internal/`, только соглашение и тест | Компилятор не защищает внутренности. `internal/` ничего не стоит |
| Разрешить модулям свободные зависимости друг от друга | Быстро возникают циклы и сцепление; невозможно реализовывать модули независимо |
| Абсолютный запрет зависимостей между некорневыми модулями, обмен данными через Core | Core получает чужие данные (результаты планировок, локации, оценки) и теряет ясную доменную ответственность |
| Заранее создать общий read model или агрегирующий модуль | Нет конкретного сценария; преждевременная инфраструктура |

## Последствия

- Имя пакета `offeranalytics` отличается от первоначального названия «Apartment Mix
  Analytics». Если бизнес не согласует объединение (Q-STR-02), модуль разделяется новым ADR.
- Новые модули регистрируются в `allowedModuleDeps`, иначе архитектурный тест упадёт.
  Разрешение зависимости между некорневыми модулями в `allowedModuleDeps` сопровождается
  комментарием со ссылкой на ADR.
- Публичный контракт Core становится ключевым: изменения в нём затрагивают все модули и
  должны вноситься осознанно.
- При проектировании Core в него включаются только данные его доменной ответственности.
  Поля «на будущее» для результатов других модулей не добавляются.
